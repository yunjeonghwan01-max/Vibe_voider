## 3. 후보 상세

### RC-00 — 리팩토링 전 회귀 확인 수단 마련 (선행 조건)
- **근거**: R-11. 자동 테스트·CI 없음. 위험 상당수가 타이밍 의존(R-01, R-02, R-07).
- **검토 내용**: 최소한의 수동 회귀 체크리스트(반격 4종·연쇄·패기·스킬 5종·궁극기·보스 2종의 핵심 장면)와, 가능하면 headless로 돌릴 수 있는 정적 검사(예: 튜닝 키 대응 검사 — 이번 감사에서 쓴 방식)를 정리.
- **주의**: 체크리스트 작성 자체는 코드 변경이 아니다. 자동화 범위를 늘리는 것은 별도 결정.
- **되돌리기**: 해당 없음.

### RC-01 — `.tscn` UID 관리 방침 결정과 정리
- **근거**: R-08 (불일치 8건, 커밋 `8a26cf4` ↔ `f0f088a` 되돌림 반복), C-7.
- **검토 내용**: 수기 UID를 유지할지, 에디터가 발급한 UID로 통일할지 **방침 결정**. 방침에 따라 에디터 재저장 1회로 정리하는 방식이 가능해 보인다 [SI].
- **주의할 결합**: `project.godot`의 `run/main_scene`가 UID로 `main.tscn`을 가리킨다(현재 일치). 씬 이동·이름 변경 리팩토링 전에 끝내는 것이 안전하다.
- **검증**: 에디터 출력의 UID 경고 0, 새로 clone한 환경에서 로딩 확인 [RU].

### RC-02 — 무적 플래그 소유권 정리 검토
- **근거**: R-01. `HurtboxComponent.invincible` 작성자: Player 17곳 + Hurtbox 타이머 + Watcher/XSlash/Prince.
- **검토할 질문**: 무적의 "이유"(피격 후·대시·스킬·반격·이벤트)를 구분해 둘 필요가 있는가? 무적 관통 공격은 "무적을 끈다"가 아니라 "이번 피격만 무시한다"로 표현할 수 있는가?
- **주의할 결합**: `HurtboxComponent`의 공개 API(`invincible`, `invincibility_duration`, `receive_hit`)는 `CLAUDE.md`가 **안정 유지**를 요구한다 — 컴포넌트 계약을 바꾸는 방향이면 명시적 승인이 필요하다. Player 쪽만으로 해결하는 범위와 컴포넌트 변경이 필요한 범위를 나눠 검토할 것.
- **검증**: 반드시 플레이테스트 (피격 직후 회전 상승·궁극기·반격, 대시 직후 피격, Watcher 광선·Knight X자·Prince 충격).

### RC-03 — Player 액션 전이의 정리 경로 통일 검토
- **근거**: R-02. `_physics_process` 321–324, `_tick_chain` 1413–1416이 현재 액션 정리 없이 `_start_parry()`.
- **검토할 질문**: "현재 액션을 떠날 때 반드시 하는 일"(판정 끄기·운반 해제·궤적 끄기·무적 원복)을 한 곳에 모을 수 있는가? 기존 `_stop_abilities()`(1700)와의 관계는?
- **주의할 결합**: 스킬별 캔슬 규칙은 **설계 의도**다 (회전 상승 캔슬 시 상승 관성 유지, 강하 착지 중 캔슬 불가 등 — `structure.md` §5). 정리 통일이 캔슬 규칙 자체를 바꾸지 않도록 구분해야 한다.
- **검증**: 플레이테스트 (슬로모션 중 공격/회전 상승 상태에서 반격, 튕겨내기 직후 연쇄).

### RC-04 — 필드몹 공격 간격 규칙 단일화 검토
- **근거**: R-06, C-6. `infantry.gd:135`, `assassin.gd:221`, `giant.gd:212` 3곳이 서로 다른 범위로 다른 클래스의 비공개 필드를 읽는다.
- **선행 질문 (인간 결정)**: 현재의 비대칭(보병은 보병만 기다림)이 의도인가, 누락인가? `structure.md:336`은 "서로 모두 기다린다"로 기술한다.
- **검토 방향 예시 (설계 확정 아님)**: "지금 공격을 치켜든 지 얼마나 됐는가"를 Enemy 공통 질의로 노출하면 3곳의 타입 분기가 사라진다.
- **영향 범위**: Phase1 필드몹 3종 + 새 필드몹. Arena 적은 무관.
- **검증**: 정적 검사 + Phase1 다수 분대 플레이로 반짝임 겹침 확인.

### RC-05 — 지침·주석 동기화
- **근거**: R-15, SRM_08 §3.4 (C-1 템플릿 서술, C-2 레벨 없음 서술, C-3 Toolkit 목록, C-4/C-5 튜닝 예외, C-6 crowd 규칙, C-12 `enemy.gd` 헤더).
- **주의**: `AGENTS.md`/`CLAUDE.md` 수정은 이번 감사 범위 밖이며 **인간 승인 사항**이다. 특히 C-1("not a game")은 AI가 프로젝트 성격을 오판하게 만들 수 있는 문구다 [SI].
- **되돌리기**: 쉬움.

### RC-06 — 스킬 슬롯 값 검증 · Ability API 이름 통일 검토
- **근거**: R-09. `Tuning.apply`는 문자열 값을 검증하지 않아 슬롯 오타가 조용히 무시된다. Ability 6종의 메서드 이름이 서로 다르다.
- **검토 방향 예시**: (a) 시작 시 슬롯 값이 알려진 스킬 이름인지 경고 출력, (b) Ability 노드의 "사용 가능?/시작/중단" 이름 맞추기. 기획 문서의 "스킬 갈아끼우기"(`VOIDER_PHASE1_DESIGN_MEMORY` §0)와 직접 연결된다.
- **주의할 결합**: `player_tuning.cfg`의 키 이름(`slot_*`)과 값 문자열은 인간이 직접 편집하는 표면이다 — 바꾸면 인간 사용법이 바뀐다.
- **검증**: 정적 검사 + 슬롯별 스킬 발동 확인.

### RC-07 — Player 표시·연출 책임 분리 검토
- **근거**: R-03, SRM_05 §8 (분리 가능성 가장 높음: 상태를 읽기만 한다). `_update_visual`(48줄), `_set_flash`, `_update_trail`, `_spawn_*` 6개(≈130줄+).
- **선례**: `PlayerVisual`이 이미 키프레임 애니메이션을 분리했다 (P-13).
- **주의할 결합**: `_squash`(26곳)·`_set_flash`(28곳)를 모든 액션 함수가 즉석에서 쓴다. `visual.modulate.a`를 `_process`(피격 깜빡임)와 `_update_visual`(회전 상승 투명도)이 함께 쓴다. 분리해도 호출 지점 수는 줄지 않을 수 있다 — **얻는 것은 "Player 파일 크기"이지 결합 감소가 아닐 수 있다** [SI].
- **검증**: 시각 확인 플레이테스트.

### RC-08 — 연쇄 반격·패기 상태 응집 검토
- **근거**: SRM_05 §8. `_chain_t`, `_chain_armed`, `_chain_skip_press`, `_chain_count`가 한 묶음이며 진입·취소 지점이 적다.
- **주의할 결합**: `_process`의 입력 읽기(313)와 `_tick_chain`의 `_start_parry()` 호출(RC-03과 겹침), 반격음 음높이가 `_chain_count`를 읽음, `_check_haki`가 반격 연출 뒤에 불려야 하는 호출 순서(`player.gd:1388-1389`).
- **권장**: RC-03과 함께 검토하는 것이 자연스럽다.

### RC-09 — 레벨 공통 골격 · Group 부여 책임 검토
- **근거**: R-05, R-14. Phase1/Arena가 group 부여·카메라 target·HUD bind·음악 루프·시차 코드를 각자 갖고, Actor 동작이 그 부여에 의존한다.
- **검토할 질문**: Actor가 스스로 속할 group(`player`, `enemy`)을 선언해야 하는가, 레벨이 부여하는 현재 방식을 문서화로 충분히 보완할 수 있는가? (후자도 정당한 선택이다.)
- **주의할 결합**: `enemy` group은 "레벨이 스폰한 적"이라는 의미도 겸한다 — 추방(`banish`)·전멸 판정이 이 의미에 기댄다. 의미를 바꾸면 Phase1/Arena 흐름이 바뀐다.
- **검증**: 두 레벨 + 치트 2·3·4~9 전부.

### RC-10 — Prince ↔ Player 이벤트 인터페이스 축소 검토
- **근거**: R-10. Prince가 `Player.Action`, `hurtbox.invincible`, `health.hp`를 직접 다룬다.
- **검토할 질문**: 보스가 Player에게 요구하는 것("입력 잠금", "방어 충격 연출", "결정타 연출", "치명타")을 Player 공개 메서드로만 표현할 수 있는가? 다른 보스도 같은 요구를 가질 것인가 (현재 사용처는 Prince 하나 — `AGENTS.md`의 "두 번째 사용처" 원칙상 지금 일반화할 근거는 약하다).
- **검증**: 왕자전 패턴 4·5, 패배·승리·재시작 (치트 9).

### RC-11 — hit-stop · 시간 기준 정책 정리 검토
- **근거**: R-07. `GameFeel.hit_stop`의 "마지막 호출 우선" 토큰, 실제 시간 연출, `_process` 입력 수집.
- **위험이 높은 이유**: 타격감 전체(전역 `Engine.time_scale`)를 건드린다. Knight 역반격 창의 체감 난이도와 직결된다.
- **권장**: 먼저 실제로 중첩 문제가 생기는지 **관측**(RU 항목 확인)하고, 문제가 확인될 때만 착수.

### RC-12 — 반격 판정 체계 구조 검토
- **근거**: R-03, R-10, SRM_05 §9.3 (새 반격 유형마다 Player의 3곳 수정).
- **위험이 높은 이유**: MCI/RCI/PRCI/CCI는 게임의 정체성이고, `_start_parry`의 분기 순서 자체가 규칙(우선순위·입력 1회 = 대상 1개)이다. 결합이 가장 많다.
- **권장**: 다른 후보 이후, 새 반격 유형 추가 계획이 실제로 있을 때 검토. **보류도 합리적이다.** PRCI 투사체 상속(P-07)처럼 Player를 건드리지 않고 확장하는 기존 방식이 당분간 충분할 수 있다.

### RC-13 — 소규모 중복 헬퍼 정리 (선택)
- **근거**: R-14 (`_ray` ×3, `_spark` 계열, `_past_screen_edge` ×2, MoonSlash/SwordWave 그리기).
- **평가**: 이득이 작고 사용처마다 미세 차이가 있다. MoonSlash는 현재 미장착이다. **다른 작업으로 해당 파일을 어차피 수정할 때** 함께 정리하는 정도가 적절해 보인다 [SI].

| Player를 기능별 Component로 일괄 분해 | 공유 상태(`action`, `velocity`, 무적, `_parry_cd`)가 넓어 분해 후에도 상호 참조가 남을 가능성이 높다 [SI]. 이득이 확인된 영역(RC-07, RC-08)부터 개별 검토 |
| 범용 상태 머신 프레임워크 도입 | `AGENTS.md:9`가 구체적 이유 없이는 금지. 현재 `Action` enum + 함수 방식은 읽기 쉽다 |
| 이름 변경 중심 리팩토링 (예: `WatcherNeedle` 개명) | 씬·스크립트·UID·문서·상속 3곳을 동시에 바꿔야 하며 동작 이득이 없다. RC-01 이후, 다른 작업과 묶을 때만 |
| 미장착 스킬(Lightning, RisingSlash, MoonSlash) 삭제 | 기획상 "교체형 슬롯"의 후보일 수 있다 — 삭제는 인간의 콘텐츠 결정 |
| Arena·구 적 4종 삭제 | 치트 8로 플레이 가능한 콘텐츠이며 Knight는 CCI 랠리의 유일한 구현 — 인간 결정 사항 |
